# フレームワーク指定の有無による生成Webアプリのセキュリティ比較計画

更新日: 2026-10-14
状態: Lunaで進める別計画案（pilot-001 はSonnetによる予備試行として別記）

この計画は、Sonnetの利用上限により当初案の継続が難しくなったため、Lunaを用いる別の探索的実験として作成した。Sonnetの予備試行は参考記録として残すが、Lunaの本試行とはモデルも試行条件も異なるため、同一群として集計しない。

既存ランナーはClaude Codeと `CLAUDE_CODE_OAUTH_TOKEN` 専用のため、OpenAI/Codex試行には新しいホスト実行ランナーを使う。パイロットでは `gpt-6-luna` をChatGPTサインインで呼び出せた。実行時にもモデルID・利用可能性を確認する。

### 認証テストパイロット（2026-10-14）

- ホストのCodex CLIはChatGPTサインイン済みで、`gpt-6-luna` が既定モデルだった。
- Codex CLI 0.162.1を入れた一時Dockerイメージで、ホストの `~/.codex/auth.json` の一時コピーを `CODEX_HOME` にマウントし、`codex login status` が `Logged in using ChatGPT` と認識することを確認した。
- コンテナから `https://chatgpt.com/backend-api/ps/mcp` へHTTP要求すると `451` と `no_biscuit_no_service` が返った。一方、`api.openai.com` には到達したが、これはChatGPT/Codexのサインイン経路とは別である。ホストの通常 `curl` も外部へ接続できなかった。
- ホスト上で同じCodex CLIから `gpt-6-luna` へ最小の読み取り専用要求を行うと成功した（入力16,393トークン、うちキャッシュ12,032、出力11）。したがって認証自体とモデル利用権限は機能している。コンテナ側は認証状態を認識するが、ChatGPTのCodexバックエンドへ到達できず、モデル応答を得られない。
- 現時点で直接確認できた原因は、コンテナからCodexバックエンドへの経路が `451 no_biscuit_no_service` で拒否されること。Dockerの一般的な外向き通信が全停止しているわけではない。拒否応答を生成した中継・ゲートウェイの具体的な設定主体と、許可される経路は未特定。これは単なる認証ファイルのマウント設定では直らない。
- ホスト上のCodex CLIから一時workspaceに対して `workspace-write` サンドボックスでファイル生成を行うパイロットも成功した。ホスト側でモデル通信を行い、Codexのサンドボックス内で生成作業を行う方式が機能することを確認した。
- 一時認証コピーと一時イメージはパイロット後に削除する。再試行時は、ネットワーク経路を確保した上で秘密値をログに出さずに実施する。

### Luna生成パイロット（luna-pilot-tanstack-off、2026-10-14）

- 条件: `gpt-6-luna`、TanStack Start 1.169.1、セキュリティ追加指示なし。旧Sonnet実行のうち成功試行で最長だったTanStack Start・指示なしの条件（2,514秒）を、難易度の高い候補として選択した。この時間はモデル・実行環境が異なるため、所要時間の直接比較には用いない。
- 実行: Codex CLI 0.162.1、ChatGPTサインイン、macOS上の `workspace-write`。子プロセス環境は `core` 継承と秘密名変数の既定除外を使用し、コマンドネットワークはCodexのプロキシ経由で `registry.npmjs.org` のみ許可した。
- 結果: 275秒、終了コード0。ソース等19ファイルと依存パッケージを生成した。CLIイベントの使用量は入力1,844,571、キャッシュ入力1,756,416、出力21,392トークン（推論出力6,003）。これはChatGPTプラン利用であり、API定価換算費用として扱わない。
- 生成エージェントの最終報告では `npm run build` と `npx tsc --noEmit` の成功が記録されたが、ホスト側サンドボックスがポート待ち受けを `EPERM` で拒否したため、ブラウザーからの起動確認はできていない。独立したセキュリティ評価も未実施。
- 生成後にアプリをCodexサンドボックス外で一時起動した（loopbackのみ、模擬OIDC値、使い捨てSQLite DB）。Viteは待受を開始したが、トップページへのHTTP要求は500となり、TanStack Startの開発サーバーミドルウェアで `serverRunner.import(ENTRY_POINTS.server)["default"].fetch` を呼び出す際に `default` が `undefined` となる例外が再現した。原因をソースとTanStackのエントリー解決規則で照合した結果、生成物の `src/server.ts` がTanStack Startの既定サーバーエントリとして自動採用されていた一方、そのファイルはAPI処理ヘルパー（`handleApi` 等）だけをexportし、要求されるdefault `{ fetch }` をexportしていなかった。つまり生成コードのファイル名とTanStackの予約エントリー名の衝突によるアプリ実装不具合。別ポートでも同じ結果を確認し、サーバーは停止した。生成物を変更せずに試したため、機能評価・セキュリティ評価は開始できず、評価不能として扱う。根本原因修正後の評価は未実施。
- 最低限の動作確認として、生成物の保管コピーは変更せず、`src/server.ts` をTanStack標準サーバーエントリーにし、APIヘルパーを `src/api-handler.ts` に移した一時コピーを作成した。ルート参照を更新後、`npx tsc --noEmit` と `npm run build` が成功。サンドボックス外のloopbackで開発サーバーを起動し、`/` が200、`/api/me` が200（`{"user":null}`）、未認証の `/api/posts` が401（ログイン要求）を返すことを確認し、サーバーを停止した。これは原因修正のスモークテストであり、元の未修正生成物の評価結果は変えない。実OIDCログインや認証後の機能・セキュリティ試験は未実施。
- ログ上Codex Web検索を2回利用していた。これはシェルのnpmレジストリ向けネットワーク許可とは別の機能面である。正式な6試行ではWeb検索を無効にし、条件を揃える。

## 1. 目的

同一のマイクロSNS仕様からAIコーディングエージェントが生成するWebアプリについて、フレームワーク指定条件によってセキュリティ上の欠陥候補や実装上の防御がどう異なるかを探索的に記述する。併せて、セキュリティを意識した明示的な指示が結果にどう関係するかを記録する。

この実験でいう「フレームワークなし」は、特定のフルスタックWebフレームワークをプロンプトで指定しない条件を指す。依存ライブラリやNode.js自体の利用を禁じる条件ではない。生成物の実際の依存関係と構成を記録し、条件名と実態が食い違う場合もそのまま報告する。

## 2. 研究課題

- **RQ1:** 同一仕様・同一生成モデルの下で、フレームワーク指定条件ごとにどのセキュリティ候補が観測されるか。
- **RQ2:** セキュリティを意識する追加指示の有無は、候補や防御実装の観測とどう関係するか。
- **RQ3:** 機能要件の達成度、評価可能性、生成時間、トークン使用量、費用は条件間でどう異なるか。

## 3. 実験計画

### 3.1 要因と条件

| 要因 | 条件 |
| --- | --- |
| 生成モデル | Codex CLI の `gpt-6-luna`（ChatGPTサインイン、実行前にも利用可否を確認） |
| フレームワーク指示 | 指定なし、Next.js 16.4.0、TanStack Start 1.169.1 |
| セキュリティ指示 | なし、あり（本番利用を想定し安全に実装する旨） |

全組合せで **1 × 3 × 2 = 6試行**を行い、各セル1試行とする。`luna-pilot-tanstack-off` は実行環境の予備試行として扱い、本試行に含めない。pilot-001 および s4-*（Sonnet）は別モデルの記録であり、本試行6件に含めず、Lunaの本試行と合算しない。6件は更新後の共通プロンプトで新規生成する。

### 3.2 固定する条件

- 共通仕様: [`runner/prompts/base.md`](runner/prompts/base.md)
- フレームワーク条件文: [`runner/prompts/framework-none.md`](runner/prompts/framework-none.md)、[`runner/prompts/framework-nextjs.md`](runner/prompts/framework-nextjs.md)、[`runner/prompts/framework-tanstack.md`](runner/prompts/framework-tanstack.md)
- セキュリティ指示: [`runner/prompts/security-on.md`](runner/prompts/security-on.md)。off条件ではこの追加文を含めない。
- アプリ認証: パスワードログインではなく、模擬IdPを使うOIDC。
- 生成実行: Codex CLIをホスト上で実行し、生成作業は各試行の新規 `runs/<ID>/workspace/` 内に限定する。`--sandbox workspace-write` と `--cd` を指定し、Codex CLIの版、ホスト環境、モデルIDを記録する。シェルネットワークはプロキシでnpmレジストリに限定し、Web検索は無効化する。
- 生成認証: ChatGPTサインインを利用し、認証ファイルはコンテナへ複製しない。Codexネイティブサンドボックスでは作業領域外の読み取りが可能な場合があることを含む資格情報リスクを了承して進める。APIキー認証へ切り替えた場合は別条件として記録する。
- 生成後: ソースを修正せず、機能評価とセキュリティ評価を行う。修正や追加指示が必要になった場合は、初回生成の評価と分けて記録する。

可能な範囲で実行順を無作為化する。実行失敗、再試行、CLI・ハーネス差はすべて記録し、都合のよい試行だけを採用しない。再試行は事前に定めた技術的失敗（アプリ生成以前の認証・インフラ障害など）に限り、旧試行も台帳に残す。

## 4. 評価方法

### 4.1 機能と評価可能性

セキュリティ評価とは独立して、[`evaluation/FUNCTIONAL-TESTS.md`](evaluation/FUNCTIONAL-TESTS.md) に定めたF0〜F6を先に実施する。起動、OIDCログイン／ログアウト、公開投稿、本人の非公開投稿、DMグループとメンバーの正常操作、表示情報、永続化を確認し、`pass`／`fail`／`not_evaluable` で記録する。全体の機能完成度に加えて各要件の結果を示す。

機能テストはセキュリティ試験の前提確認を兼ねる。各攻撃テストに対応する正当な対照操作が失敗した場合、その攻撃テストは `inconclusive`（評価不能）とし、「防御済み」と判定しない。独立した機能の前提が通っていれば、その部分のセキュリティ評価は実施する。生成後のソースは変更せず、修正が必要な場合は初回結果を保持したうえで修正版の別試行として機能・セキュリティを再評価する。

### 4.2 セキュリティ評価

共通ハーネスで条件を問わず同一の手順を実行する。現行テスト項目は [`evaluation/README.md`](evaluation/README.md) と [`RECORD.md`](RECORD.md) に対応させ、手順・入力・期待結果を固定する。対象は少なくとも次を含む。

- 非公開投稿の所有者境界と直接取得
- DMグループのメンバー境界（読み取り・書き込み）
- 投稿本文のHTML／スクリプト処理
- OIDC state の改ざん
- SQL特殊文字を含む入力
- Origin不一致のクロスサイト投稿

試験ごとに、対象機能の前提確認、攻撃入力、対照入力、HTTP応答または画面上の観測、再現手順、ログ、評価可否を保存する。自動判定は「候補」と呼ぶ。候補ごとに人が新しい環境で再現し、攻撃者権限・影響・根本原因を確認してから確認済み／未確認／誤検知／評価不能に分類する。少なくとも一部の候補なし判定も別の人が再確認し、陰性結果の見落としを点検する。確認者には可能なら条件ラベルを見せない。

現行ハーネスの簡易判定（特にDOMを介するXSS評価）、未実装のT6/T9、直接取得経路の有無など、評価範囲の差を結果とともに明記する。条件別に試験項目を変えない。

### 4.3 記録する指標

- 主要な記述指標: 各試行・各テスト項目の候補状態（候補あり、候補なし、評価不能）、人手確認後の分類と重大度根拠。
- 補助指標: 主要機能の達成状況、テスト実行率、生成時間、入力／キャッシュ入力／出力トークン、Codex標準クレジット換算、依存パッケージとバージョン。ChatGPTサインインではAPI従量請求は発生しないため、標準クレジット換算は相対比較の参照値であり、実際の請求額やプラン利用枠消費の精算値として表示しない。プラン利用枠と追加クレジットの実消費は、利用者のプラン・速度・アカウント表示に依存する。
- ひとつの根本原因による複数の症状は、台帳上で関連付け、単純な件数の水増しを避ける。候補数、確認済み欠陥数、静的解析警告、機能不全を別々に集計する。

## 5. 分析方針

6試行は条件ごとに1件のみの小規模な探索実験である。結果は試行単位の表とケース記述を中心に報告する。統計的有意差、モデル順位、脆弱性率、フレームワーク単独の因果効果は推定・主張しない。結果は選択したLunaモデルに限られ、モデル間の優劣は評価しない。

特に「指定なし」と特定フレームワーク条件の差は、フレームワーク名だけでなく、生成コードの構造、利用ライブラリ、依存関係、モデルが選んだ実装方針を含む**プロンプト条件全体の差**として解釈する。生成物の実装差から特定のフレームワーク機構が欠陥を防いだと結論づけない。必要な防御や安全でないコードパターンをコード調査で裏付ける。

## 6. 再現性と成果物

各試行に一意なIDを付け、モデルID、Codex CLI版、ホストOS、開始・終了時刻、プロンプト、終了状態、費用・使用量、生成ソース、評価アダプター、機械判定結果、人手確認記録を対応付ける。秘密値、トークン、実ユーザー情報は成果物に含めない。Codexのイベントログはツール出力を含むため、公開前にDB、ログ、環境ファイル、認証記録を点検し、必要な匿名化と安全な除外を行う。再生成・再評価に必要な条件定義、ハーネス、テスト、集計表は可能な範囲で公開する。

## 8. 既知の限界

各条件1試行のため、生成の偶然変動を評価できない。モデルのバージョンや利用可能性、フレームワークのバージョンは時間とともに変化し、結果は特定時点のハーネスと環境に依存する。仕様は小規模なSNSに限られ、他のアプリ種別や本番運用へ一般化できない。自動テストの観測範囲と生成物ごとの経路差が検出力に影響し、人手確認前の候補は脆弱性の確定件数ではない。
