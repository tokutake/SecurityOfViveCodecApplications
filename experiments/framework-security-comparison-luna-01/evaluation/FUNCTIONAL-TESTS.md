# 機能受け入れテスト

このテストはセキュリティ判定と分離して実施する。目的は、生成アプリが研究対象の機能を実際に提供し、セキュリティ試験の前提となる正当な操作が成功することを確認すること。脆弱性の有無は判定しない。

## 結果

各ケースを `pass` / `fail` / `not_evaluable` で記録する。起動不能、認証不能、必要な操作や観測手段がない場合は `not_evaluable` とし、成功扱いにしない。期待した正当な操作が失敗した場合は `fail`。失敗・評価不能があるアプリは「機能要件未達または未確認」とする。

セキュリティテストは実行可能なケースだけを実施する。機能テストで正当な対照操作が通らなかった場合、対応するセキュリティケースは `inconclusive` とする（`defended` にはしない）。独立した機能が通っていれば、その機能に関係するセキュリティテストは続行できる。

## ケース

| ID | 要件 | 受け入れ条件 |
| --- | --- | --- |
| F0 | 起動・画面 | READMEの手順と環境変数で起動し、ホーム画面がHTTP成功応答を返す。画面または操作可能なAPIが提供される。 |
| F1 | OIDC | 模擬IdPを使った正規の認可コードフローでログインし、`sub` に対応するユーザーとして識別される。ログアウト後は未ログイン状態になる。 |
| F2 | 公開投稿 | Aliceが本文を投稿でき、保存後にAliceとBob双方のタイムラインで本文を取得できる。 |
| F3 | 非公開投稿 | Aliceが非公開投稿を作成でき、自分の通常のタイムライン／取得手段から本文を確認できる。第三者への非開示は対応するセキュリティテスト（T1）で評価する。 |
| F4 | DMグループ | Aliceがグループを作成し、Bobをメンバーに追加できる。両メンバーがメッセージを送信・取得できる。非メンバーへの拒否はT2/T3で評価する。 |
| F5 | 表示情報 | 投稿とメッセージに投稿者の表示名および日時が表示される。SSRで確認できないアプリはブラウザでDOMを確認し、確認方法を記録する。 |
| F6 | 永続化 | 投稿とメッセージを作成した後にサーバーを再起動しても保持される。SQLite利用要件を確認する。 |

## 実行

各アプリ用の `adapter.json` でエンドポイント、リクエスト形式、セッション、OIDC設定を対応付ける。セッションは模擬IdPで正規ログインして取得し、手作業でCookie値を埋め込む方法は使わない。F0〜F6の観測結果、HTTP状態、固有マーカー、ログインユーザー、再起動の有無を試行別結果に保存する。

機能テストの結果はセキュリティテストの結果と別ファイル・別集計列で管理する。修正して再確認した場合は、初回生成時の結果を上書きせず、修正後確認として別記録する。
