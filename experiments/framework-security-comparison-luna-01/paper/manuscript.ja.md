# フレームワーク指示とセキュリティ指示はAI生成Webアプリの安全性にどう関係するか：6条件の探索的研究

**原稿の位置づけ:** 探索的パイロット報告。結果は予備的であり、査読前。
**実験:** Luna study 01
**日付:** 2026年10月14日

## 要旨

AIコーディングエージェントは、フレームワーク指定やセキュリティ指示の異なる条件で類似のアプリを生成できるが、生成物のセキュリティ結果がどう異なるかは明らかでない。本稿では、Codex CLIと`gpt-6-luna`を用い、マイクロSNSアプリを6条件で各1回生成した探索的研究を報告する。条件は、フルスタックフレームワークを指定しない、Next.jsを指定する、TanStack Startを指定する、の3条件と、追加のセキュリティ指示の有無を組み合わせたものである。事前に定めた機能受け入れゲートを実施し、必要な機能が通過した場合に限って自動セキュリティ試験を行った。6アプリ中4つが7項目すべての機能試験に合格した。そのうち3つでOrigin/CSRF試験の自動候補が出たが、いずれも人手による独立再現は未実施である。セキュリティ指示あり・フレームワーク指定なしの条件は全機能試験に合格し、自動候補はなかった。一方、対応するセキュリティ指示なしの条件も全機能試験に合格したが、候補が1件あった。この単一の対比から、どちらかの指示条件がより安全だとは結論できず、「フレームワーク指定なしが最善」とも結論できない。セキュリティ指示ありのフレームワーク2条件は機能試験に失敗し、セキュリティ結果は得られていない。生成時間の合計は25分45秒だった。各条件1回のみで、一部試験は不完全または評価不能であり、候補も未確認であるため、本研究が支持するのは記述的な観察と、追試および人手確認の必要性に限られる。

**キーワード:** AI生成ソフトウェア、アプリケーションセキュリティ、Webフレームワーク、セキュリティ指示、機能テスト、探索的研究

## 1. はじめに

AIコーディングエージェントは、自然言語の仕様からWebアプリケーション全体を生成する用途で使われ始めている。フレームワークの指定や明示的なセキュリティ指示は、生成される構成や実装に影響する可能性がある。しかし観測差は、モデルの生成ゆらぎ、依存ライブラリ、個別の実装選択、実行環境などによっても生じる。小規模な比較実験は、失敗例や評価方法を見つける助けになるが、反復生成と確実なセキュリティ確認がなければ一般的な優劣は示せない。

本稿では、同じマイクロSNS仕様から、1つのモデルおよびエージェント版を用いて生成した6つのアプリを記述する。プロンプトでフルスタックフレームワークを指定するかどうか、追加のセキュリティ指示を含めるかどうかを変えた。機能評価とセキュリティ評価を分け、未実装または動作しない機能をセキュリティ上の成功と誤って数えないようにした。

本研究は探索的である。ここでいう「フレームワーク指定なし」は、プロンプトで特定のフルスタックフレームワークを指定しなかったことを意味する。生成アプリがライブラリやランタイムのフレームワーク要素を使わなかったという意味ではない。

### 研究課題

- **RQ1:** フレームワーク指示およびセキュリティ指示の各条件で、どのような自動セキュリティ試験結果が観測されたか。
- **RQ2:** 生成アプリのうち、機能受け入れ条件を満たし、セキュリティ評価の対象となったものはいくつか。
- **RQ3:** 6試行で観測された生成時間とトークン使用量はどの程度か。

## 2. 方法

### 2.1 実験計画

フルスタックフレームワークの指定なし、Next.js、TanStack Startの3条件と、追加のセキュリティ指示の有無を組み合わせた3×2の探索的計画を用いた。6条件それぞれで1回生成した。共通仕様は、OpenID Connect（OIDC）ログイン、公開投稿、非公開投稿、ダイレクトメッセージグループ、投稿者と日時の表示、SQLite永続化を備えた小規模なSNSアプリを求めるものだった。フレームワーク条件とセキュリティ条件は、共通仕様に対するプロンプト追記として実装した。

実行順は実験前に記録した。エージェントはChatGPTサインイン経由の`gpt-6-luna`を使用したCodex CLI 0.162.1である。macOS上で実行し、評価時の生成アプリはloopbackにバインドした。OIDCには使い捨ての模擬IdPとダミー資格情報を使用した。実ユーザーアカウントや本番資格情報は使用していない。

### 2.2 機能受け入れゲート

セキュリティ試験に先立ち、7項目（F0〜F6）を評価した。起動とホーム画面応答、OIDCログイン・ログアウト、公開投稿の作成と取得、非公開投稿の作成と所有者による取得、DMグループとメンバー操作、投稿者と日時の表示、実プロセス再起動後の永続化である。各項目を合格、不合格、評価不能として記録した。正当な操作が失敗した場合、それを防御済みとはせず、対応するセキュリティ試験は評価不能とした。本研究では7項目すべてに合格したアプリのみ、セキュリティ試験へ進めた。

### 2.3 セキュリティ試験

自動ハーネスでは、非公開投稿へのアクセス、DMの読み取り・書き込み境界、HTML/スクリプト処理、OIDC state改ざん、SQL特殊文字処理、クロスオリジン要求処理を評価した。T6とT9はハーネスに未実装だった。さらに、一部の試験には観測上の制限があった。T4はブラウザー描画の確認が必要な場合があり、T5では正常なOIDCコールバック対照が成功する必要があり、T8ではブラウザーのSameSite Cookie動作を再現していない。自動試験でいう「候補」は人手で再現確認すべき兆候であり、確認済み脆弱性として数えない。

### 2.4 指標と分析

各試行の機能状態、実施可能だった自動セキュリティ結果、生成時間、トークン数を報告する。条件ごとの記述的な比較に限り、統計的有意差検定、脆弱性率の推定、各条件1観測からの因果効果の推定は行わない。「参考クレジット」は比較用に標準トークンレートへ換算した値であり、実際のプラン請求額やサブスクリプション利用枠の消費量ではない。

## 3. 結果

### 3.1 機能およびセキュリティ結果

| プロンプト条件 | 機能ゲート | 自動セキュリティ結果 |
|---|---:|---|
| フレームワーク指定なし・セキュリティ指示あり（`none-on`） | 7/7合格 | 7項目で防御を観測、候補なし |
| フレームワーク指定なし・セキュリティ指示なし（`none-off`） | 7/7合格 | 6項目で防御を観測、T8候補あり |
| Next.js・セキュリティ指示なし（`nextjs-off`） | 7/7合格 | 4項目で防御を観測、T4・T5は評価不能、T8候補あり |
| Next.js・セキュリティ指示あり（`nextjs-on`） | F0合格、F1不合格、F2〜F6評価不能 | 機能ゲート不通過のため未実施 |
| TanStack Start・セキュリティ指示なし（`tanstack-off`） | 7/7合格 | 6項目で防御を観測、T8候補あり |
| TanStack Start・セキュリティ指示あり（`tanstack-on`） | F0不合格、F1〜F6評価不能 | 機能ゲート不通過のため未実施 |

T8候補は、機能が完成した4アプリのうち、追加のセキュリティ指示を含めなかった3アプリで観測された。候補は人手で再現されておらず、ハーネスはブラウザーのSameSite Cookie動作を模擬していない。したがって、これは未確認の自動シグナルであって、確認済みCSRF脆弱性が3件あったことを示さない。フレームワーク指定なし・セキュリティ指示ありの1試行で候補がなかったことも、安全性の証明ではない。

追加のセキュリティ指示がないNext.jsアプリでは、T4とT5が評価不能だった。T4はJSON応答でブラウザー描画時の挙動を確認できず、T5は正常なコールバック対照が失敗したためstate改ざんとの比較が成立しなかった。これらを防御済みとは数えていない。

追加のセキュリティ指示があるNext.jsアプリではホーム画面が表示されたものの、模擬IdPのログインコールバック後にセッションが確立せず、`/api/me`は未認証状態を返した。根本原因は完全に特定できていない。追加のセキュリティ指示があるTanStack Startアプリは、ランタイムが要求するfetch handlerをサーバーエントリーがexportしなかったため、起動時にHTTP 500を返した。いずれも機能ゲートを通過せず、セキュリティ結果は得られていない。安全とも危険とも解釈できない。

## 4. 考察

最も重要な観察は、「指示なし・フレームワークなしが一番だった」ということではない。フレームワーク指定なしの2条件では、セキュリティ指示ありのアプリに自動候補がなく、指示なしのアプリに未確認のT8候補が1件あった。しかし、条件ごとに1回しか生成していないため、生成の偶然変動や実装の細部が差を生んだ可能性がある。また、この候補はブラウザー動作を考慮した人手再現が必要である。今回の結果は、この1回では明示的なセキュリティ指示が助けになった可能性とは整合するが、その効果を立証しない。

フレームワークの安全性も均等に比較できていない。フレームワーク指定とセキュリティ指示を併用した2条件は機能要件を満たさず、セキュリティ試験を実施していない。一方、セキュリティ指示のない条件では、機能を満たした3種類のアプリでT8候補がそれぞれ観測された。ただし、各条件1回であることとハーネスの限界から、フレームワーク間の順位付けはできない。さらに、フレームワーク名の指定はプロンプトへの介入であり、アーキテクチャ、ライブラリ、生成コードをまとめて変えうる。この設計ではフレームワーク固有の効果を分離できない。

機能ゲートを置いたことで、「試験未実施」と「防御を観測」を区別できた。セキュリティ評価の準備ができていないアプリが2つあることを表に出し、通常の操作が失敗したことをセキュリティ上の防御として数えるのを避けられた。生成ソフトウェア研究では、対象機能と正当な対照操作が動作して初めて、セキュリティ試験結果に意味が生じる。

生成使用量には6試行間で差があったが、各条件1回の記述値にすぎない。特に参考クレジットを実支出やプラン利用量として報告してはならない。生成コストの比較には反復が必要である。

## 5. 限界と次の課題

本研究は、1セル1試行、1モデル、1エージェント版、1アプリ仕様、1評価環境による6試行のパイロットである。結果を他モデル、他タスク、他バージョン、他の配置環境へ一般化できない。セキュリティ評価は自動化され、範囲も不完全である。T6とT9がなく、一部結果は評価不能、T8はブラウザーのSameSite動作を扱っておらず、候補は未確認である。2条件は機能ゲートを通過せず、セキュリティ結果がない。Next.js/OIDC失敗の正確な原因も未解決である。

強い結論を出す前に、T8候補を人手で再現・分類し、候補なしの結果の一部を独立に確認する必要がある。Next.js/OIDC失敗を調査し、機能不全条件を修正して再実験するかを決める場合は、修正前の初回評価と分けて記録する。確認的研究では、各条件で独立生成を複数回行い、停止・再試行規則を事前に定め、可能な範囲で条件ラベルを伏せたレビューを行い、機能達成度、試験範囲、確認済み所見、資源使用量を分けて報告すべきである。

## 6. 結論

本パイロットでは、フレームワーク指定なし・セキュリティ指示ありで生成したアプリが全機能試験に合格し、自動セキュリティ候補はなかった。同じくフレームワーク指定なしでセキュリティ指示を含めなかったアプリも機能試験には合格したが、未確認のOrigin/CSRF候補が1件あった。これらの観察から、どちらかの条件が最も安全だとは立証できず、フレームワーク指定がない方が安全とも示せない。本研究が示すのは、AI生成アプリの安全性を比較する際には、機能受け入れ、セキュリティ評価の実施可否、候補の確認、生成の反復を併せて報告する必要があるという点である。
